==================================================

1. Technology and compatibility

- Python 3.12.
- Official PyPI "mcp" SDK, preferably version 2.3.0.
- Pydantic v2.
- Use only documented, public SDK APIs.
- Pin tested dependency versions.
- Use the official SDK transport and protocol machinery.

IMPORTANT:
The high-level MCPServer API may return isError=true for schema validation failures, whereas this assessment explicitly requests JSON-RPC error codes.

Investigate this difference and favor the official low-level mcp.server.Server API if needed.

For failed tools/call argument validation, return a JSON-RPC protocol error with code -32602, not merely a successful JSON-RPC result containing isError=true.

Use MCPError and INVALID_PARAMS from the official SDK where appropriate.

Do not monkeypatch SDK internals.

2. Input schema definitions

Implement reusable Pydantic schemas.

get_customer_record:
- customer_id required
- Must match ^CUST-[0-9]{5}$
- Reject missing, null, nonstring, and malformed values
- Reject additional fields

trigger_refund:
- customer_id required, same validation
- amount required, numeric, finite, strictly greater than zero
- reason required, string, minimum length 10
- Reject unknown fields
- Reject numeric strings, booleans, null, NaN, and Infinity
- Reject blank/whitespace-only reasons
- Do not silently coerce invalid input types

Accept valid positive JSON numeric values such as 10, 10.5, and 10.25. Do not introduce an undocumented two-decimal-place input restriction.

Use Decimal(str(amount)) or a similarly defensible technique for internal financial arithmetic. Do not use binary floating-point arithmetic for refund balance updates.

Generate tools/list inputSchema from the same Pydantic models, or otherwise prove that advertised JSON Schema matches actual validation.

3. JSON-RPC error handling

Enforce and test these categories:

- Malformed JSON: -32700 Parse error.
- Invalid JSON-RPC request structure: -32600 Invalid Request.
- Unknown protocol method: -32601 Method not found.
- Invalid tool arguments: -32602 Invalid params.
- Unknown tool name: -32602 Invalid params.
- Unexpected internal protocol failure: -32603 Internal error.

Use official SDK handling whenever possible.

Preserve the request ID in applicable error responses.

Distinguish protocol errors from business execution errors.

Business execution failures, such as a well-formed but nonexistent customer, should return MCP tool results marked isError=true, rather than being mislabeled as malformed JSON-RPC requests.

Never leak Python stack traces or internal implementation details in client-facing errors.

If the SDK cannot produce a required error response on a malformed transport message, document the exact limitation and provide a failing or diagnostic wire test. Do not falsely report protocol compliance.

4. STDIO transport

Implement a runnable executable entry point that starts the MCP server over stdio.

Requirements:
- Read MCP messages through the SDK's stdio transport.
- Emit valid JSON-RPC messages through stdout.
- No print(), debug output, startup banners, or other nonprotocol text on stdout.
- Configure Python logging exclusively to stderr.
- Clean startup and shutdown.
- Do not launch an HTTP server.
- Do not require a listening TCP port.

5. Mock customer data

Create a deterministic in-memory customer repository.

Seed at least three records:
- CUST-00001
- CUST-00002
- CUST-00003

Include minimal non-sensitive fields, such as:
customer_id, customer_name, account_status, refundable_balance.

get_customer_record should return structured customer data for existing IDs.

For missing customers, return an appropriate business-level tool error.

Avoid real personal or financial data.

6. Mock refund behavior

trigger_refund should:
- Validate all inputs before side effects.
- Confirm the customer exists.
- Check that the requested refund does not exceed the available refundable balance.
- Record successful refund transactions in memory.
- Deduct successful refunds from the available refundable balance.
- Return a deterministic refund identifier and status.
- Avoid balance mutations when validation or execution fails.

A deterministic sequential refund identifier is sufficient.

No real payment integrations or database are required.

Define the state lifecycle explicitly: in-memory mock state lasts only for the running server process.

Do not claim persistence across restarts.
